# EXP 5 – Comparing Prompting Techniques Through Engineering Problem-Solving Scenarios

## 1. Aim
To compare different prompting techniques and evaluate their effectiveness in solving a real-world engineering problem selected from a final-year project, using relevance, accuracy, completeness, clarity, feasibility and usefulness as evaluation criteria.

## 2. AI Tools Required
- ChatGPT – prompt execution, solution generation and comparative analysis.
- Markdown editor or Visual Studio Code – documentation.
- Python 3 (optional) – independent execution of the proposed engineering validation tests.

## 3. Project Title and Problem Statement
**Project:** A Hybrid Blockchain–IPFS and Generative-AI Framework for Emergency Blood Resource Discovery: Design and Prototype Evaluation.

The project aims to help users discover blood resources by extracting structured search criteria from natural-language requests and retrieving relevant blood-bank inventory records. Blockchain supports authorization and provenance of registry updates, while IPFS supports off-chain inventory storage. Neither technology independently guarantees that physical stock is available.

**Engineering problem:** Design a reliable discovery filter that handles blood-group matching, requested quantity, registry verification, active status and distance ranking without presenting unverified or unsuitable inventory as confirmed availability.

## 4. Selected Engineering Scenario
A user submits the typed English request: **“Need 2 units of O+ blood urgently.”** The AI extracts the blood group, quantity and urgency. A deterministic application component then filters inventory and ranks eligible blood banks by distance.

For this controlled experiment, use the following synthetic records. Distance is supplied in kilometres; it is not calculated from real coordinates. Quantity is assumed to represent comparable reported units of the requested inventory item, not a clinical compatibility determination.

| Bank | Blood group | Reported units | Verified | Active | Distance (km) |
|---|---|---:|---|---|---:|
| A | O+ | 3 | Yes | Yes | 4.2 |
| B | O- | 5 | Yes | Yes | 1.0 |
| C | O+ | 8 | No | Yes | 0.8 |
| D | O+ | 1 | Yes | Yes | 2.0 |
| E | O+ | 4 | Yes | No | 1.5 |
| F | O+ | 2 | Yes | Yes | 6.1 |
| G | O+ | 2 | Yes | Yes | 3.1 |

**Expected engineering result:** G → A → F. Exact group matching is an application search rule, not a transfusion compatibility rule. All results must be described as reported inventory requiring direct confirmation from the blood bank.

## 5. Experimental Procedure
1. Select the engineering problem and fix the test records.
2. Use the same scenario and records as a common context for every prompt below.
3. Generate a response using a naïve prompt and four improved techniques: structured zero-shot, persona, few-shot and decomposition.
4. Compare the generated responses using a common evaluation rubric.
5. Select the most suitable technique and refine it into an implementation-ready prompt.
6. Validate the proposed deterministic algorithm against independently specified expected results.

**Experimental control:** The five responses below are generated by ChatGPT for this submission using the same scenario. They are not transcripts of five independently executed API calls. No timing, repeated-run consistency or live hospital stock is measured. The evaluation is a descriptive, rubric-based comparison, not a statistically controlled model benchmark.

## 6. Prompts and AI-Generated Outputs

### Technique 1 – Straightforward / Naïve Prompt (Baseline)

**Prompt**
> Suggest a method to find blood banks for a user who urgently needs two units of O+ blood. Use the supplied inventory records.

**AI-generated output**

Use a natural-language model to identify the required blood group and quantity. Search the blood-bank database for O+ inventory containing at least two units. Prefer verified and active blood banks and sort results by distance. Provide the contact information so the user can confirm availability. Based on these conditions, the suitable records are G, A and F.

**Observation:** The result is correct for the supplied case, but “prefer” does not establish mandatory exclusion. The response also lacks input validation, tie-breaking rules and tests.

### Technique 2 – Structured Zero-Shot Prompt (Basic Improved Prompt)

**Prompt**
> Design a blood-resource discovery algorithm for the supplied request and inventory. Extract bloodGroup, quantity and urgency. Require exact blood-group equality, sufficient reported quantity, verified=true and active=true. Sort eligible records by ascending distance and use bank ID as a tie-breaker. Return a JSON extraction example, ranked results, rejection reasons and a short explanation. Reject invalid input and never claim confirmed physical stock.

**AI-generated output**

```json
{"bloodGroup":"O+","quantity":2,"urgency":"urgent"}
```

Apply the four eligibility conditions using logical AND, then order by distance and bank ID. Reject missing or unsupported blood groups and non-positive or non-integer quantities rather than guessing. Exclude records with invalid distances or missing mandatory fields.

| Rank | Bank | Units | Distance (km) |
|---:|---|---:|---:|
| 1 | G | 2 | 3.1 |
| 2 | A | 3 | 4.2 |
| 3 | F | 2 | 6.1 |

B fails exact group matching; C fails verification; D has insufficient reported quantity; E is inactive. Contact the blood bank to confirm current stock. The AI extracts criteria; the application enforces eligibility.

**Observation:** Explicit constraints make the output more reproducible and auditable. No executable implementation or detailed tests are provided.

### Technique 3 – Persona Prompting

**Prompt**
> Act as a senior software engineer specializing in reliable healthcare information systems. Design the discovery component for the supplied scenario. Enforce exact group equality, sufficient reported units, verified and active registry status, valid distances and deterministic distance/ID ranking. Explain architecture, trust boundaries, failure handling, suitable records and safety limitations. Do not offer transfusion advice.

**AI-generated output**

Use a pipeline consisting of request parsing, schema validation, registry retrieval, deterministic filtering and presentation. Treat the language model output and IPFS inventory as untrusted inputs until validated. Registry authorization establishes who submitted or approved a record, not whether the physical inventory is accurate. Require all eligibility conditions; exclude B, C, D and E. Return G (3.1 km), A (4.2 km) and F (6.1 km).

If a required field is absent, request clarification; if a bank record is malformed, exclude it and log the reason. If registry or storage retrieval fails, report a service failure rather than a misleading empty result. Present reported quantities and advise direct confirmation. Never infer clinical compatibility or prioritize unverified results merely because a request is urgent.

**Observation:** Strong architectural and safety reasoning. The answer does not include a concrete algorithm implementation or a systematic test suite.

### Technique 4 – Few-Shot Prompting

**Prompt**
> Follow these examples of discovery filtering:
> - O+, 2 units; record O+, 2 units, verified=true, active=true, valid distance → eligible.
> - O+, 2 units; record O-, 5 units, verified=true, active=true, valid distance → reject: group mismatch.
> - O+, 2 units; record O+, 5 units, verified=false, active=true → reject: unverified.
> - O+, 2 units; record O+, 1 unit, verified=true, active=true → reject: insufficient units.
> - O+, 2 units; record O+, 5 units, verified=true, active=false → reject: inactive.
>
> Apply the same rules to the supplied scenario. Reject malformed inputs and records, rank eligible banks by distance then ID, and return one decision for every record. Label quantities as reported, not confirmed.

**AI-generated output**

| Bank | Decision | Reason |
|---|---|---|
| A | Eligible | All eligibility conditions satisfied |
| B | Rejected | Group mismatch |
| C | Rejected | Unverified |
| D | Rejected | Insufficient reported units |
| E | Rejected | Inactive |
| F | Eligible | Exactly two reported units satisfies threshold |
| G | Eligible | Exactly two reported units satisfies threshold |

Ranked result: G → A → F. Missing or malformed required fields must not be treated as a successful match. The returned quantities are reported inventory only; contact the blood bank to confirm stock.

**Observation:** Examples encourage consistent classification and explicitly demonstrate the quantity boundary. The output is useful for audit logs but lacks system-level architecture and implementation.

### Technique 5 – Task Decomposition / Step-by-Step Structured Prompting

**Prompt**
> Solve the supplied blood-discovery engineering problem in stages. (1) Define inputs and validation. (2) Separate AI extraction from deterministic filtering. (3) Specify exact eligibility and distance/ID sorting. (4) Apply the rules to each supplied record and give the ranked results. (5) Provide executable Python or precise pseudocode. (6) Specify tests for boundary conditions, malformed data, ties, empty results and service failures. (7) Explain trust limitations and safe presentation. Provide concise engineering justifications, not hidden reasoning. Do not infer compatibility or confirm physical availability.

**AI-generated output**

1. Extract `bloodGroup`, `quantity` and `urgency` from the request. Require a supported group and positive integer quantity; request clarification if ambiguous. Urgency is metadata and never bypasses eligibility.
2. Retrieve authorized registry and inventory data; distinguish retrieval failure from a successful retrieval containing no matches.
3. Accept a record only when its group exactly matches the request, reported quantity meets the threshold, verification and active flags are both true, and distance is finite and non-negative. Reject malformed records.
4. A, F and G pass; B (group), C (verification), D (quantity), E (active status) fail. Sort by `(distance, bank_id)` to obtain G → A → F.
5. Use the reference implementation in Section 11, which separates deterministic search from AI extraction.
6. Test quantity equality, group mismatch, inactive and unverified records, missing fields, malformed quantities, invalid distances, ties and no results. Simulate service failure at the integration boundary.
7. Display the reported quantities and distances with an explicit instruction to contact the bank. Neither blockchain authorization nor content addressing proves physical stock availability.

**Observation:** Produces the most implementation-oriented response because it explicitly requests validation, algorithm, test cases and trust boundaries. It is longer than necessary for a simple lookup.

## 8. Analysis and Observations

- All five responses identify the correct ranked result for the normal scenario. A naïve prompt can therefore be equally effective for a simple, well-defined lookup.
- Structured zero-shot prompting improves clarity by explicitly defining mandatory conditions and output format. It removes ambiguity between preferring verified banks and requiring verification.
- Persona prompting adds domain-specific architecture, error handling and trust boundaries, but assigning an expert role alone cannot guarantee correctness.
- Few-shot prompting makes classification consistent and provides clear rejection explanations. Its usefulness depends on the representativeness and correctness of examples.
- Task decomposition covers implementation and testing more comprehensively, but increases prompt and response length.
- Improved prompts do not universally guarantee better responses. Incorrect constraints or examples can cause systematic errors. This experiment cannot establish consistency across repeated runs.

## 9. Final Selected Prompting Technique
**Task decomposition** is selected for this engineering problem because it provides traceable requirements, deterministic logic and a testable implementation. Structured zero-shot is a suitable lower-cost alternative for routine searches; few-shot examples may be incorporated into the extraction stage.

## 10. Refined / Final Prompt

> Act as a software engineer designing a safety-conscious blood-resource discovery component for a hybrid blockchain–IPFS system. Use the supplied English request and inventory fixture. Separate natural-language extraction from application-side filtering. Extract only bloodGroup, quantity and urgency; return a clarification request for missing or invalid fields. Never infer transfusion compatibility. Validate schema and registry data, require exact group match, sufficient reported units, verified=true and active=true, and finite non-negative distance. Sort by distance then unique bank ID. Return a ranked table, rejection reasons, a deterministic Python implementation and unit tests for normal, boundary, malformed, empty and tie cases. Distinguish service failure from no eligible records. Describe blockchain and IPFS trust limitations. Label every result as reported inventory requiring direct confirmation. Do not claim clinical validation or actual stock availability.

## 11. Engineering Validation

### Reference Python implementation

```python
from math import isfinite

GROUPS = {"A+", "A-", "B+", "B-", "AB+", "AB-", "O+", "O-"}

def discover(group, quantity, records):
    if not isinstance(group, str) or group not in GROUPS:
        raise ValueError("Invalid blood group; clarification required")
    if type(quantity) is not int or quantity <= 0:
        raise ValueError("Invalid quantity; clarification required")
    if not isinstance(records, list):
        raise ValueError("Inventory unavailable or malformed")
    eligible = []
    for r in records:
        if not isinstance(r, dict):
            continue
        d = r.get("distance")
        units = r.get("units")
        bank = r.get("id")
        if not isinstance(bank, str) or not bank.strip():
            continue
        if type(d) not in (int, float) or not isfinite(d) or d < 0:
            continue
        if type(units) is not int or units < quantity:
            continue
        if (r.get("group") == group and r.get("verified") is True
                and r.get("active") is True):
            eligible.append(r)
    return sorted(eligible, key=lambda r: (r["distance"], r["id"]))
```

The fixture assumes unique bank IDs and comparable units. A production adapter must enforce uniqueness, inventory item identity, timestamp/freshness policy and upstream retrieval integrity. This function does not implement live blockchain/IPFS retrieval, natural-language extraction or geolocation.

## 13. Conclusion

The experiment demonstrates how prompt design affects the completeness, clarity and engineering usefulness of AI-generated solutions. The straightforward prompt solved the normal lookup, while the improved prompts specified stronger requirements and addressed failure conditions. Task decomposition received the highest rubric score because it requested implementation, validation and trust limitations explicitly. Deterministic filtering remains necessary because a fluent AI response alone does not establish engineering correctness. Further evaluation should use independently executed prompts, multiple runs, live integration tests and independently reviewed scoring.

## 14. Result

The prompts for the selected engineering problem were executed successfully as a comparative ChatGPT exercise, and the proposed deterministic reference filter passed all 15 synthetic validation checks. Task decomposition was selected as the most suitable technique under the stated evaluation rubric.
